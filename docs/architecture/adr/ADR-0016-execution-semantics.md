# ADR-0016: Execution Semantics

* **Status**: Draft
* **Date**: 2026-07-29
* **Author**: Enterprise Architecture Board

## Context
E-COS handles complex operational graphs that combine API requests, long-running agent reasoning, and human-in-the-loop approvals. Operating in a distributed system means tasks will fail, times will outrun, and networks will drop packets. 

To ensure system consistency, prevent duplicate actions (e.g., executing marketing budgets twice), and manage long-running tasks gracefully, we need a formalized **Execution Semantics** specification.

## Decision
All task and workflow executions in E-COS must conform to the following execution semantics rules:

```
                    ┌──────────────────────────────┐
                    │      E-COS Task Runner       │
                    └──────────────┬───────────────┘
                                   │
                [Verifies Idempotency / Deduplication]
                                   ▼
                    ┌──────────────────────────────┐
                    │      Task Execution Loop     │
                    └──────────────┬───────────────┘
                                   │
               ┌───────────────────┴───────────────────┐
               │                                       │
     [Success / Complete]                     [Failure Encountered]
               ▼                                       ▼
    ┌──────────────────────┐               ┌───────────────────────┐
    │ Save Output Payload  │               │   Apply Retry Logic   │
    └──────────────────────┘               │ (Backoff + Jitter)    │
                                           └───────────┬───────────┘
                                                       │
                                            [Exceeded Max Retries]
                                                       ▼
                                           ┌───────────────────────┐
                                           │   Saga Compensator    │
                                           │  (Rollback Protocol)  │
                                           └───────────────────────┘
```

### 1. Synchronous vs. Asynchronous Execution
- **Synchronous Execution**: Block execution until task outputs are available. Max duration limit is strictly **10,000ms**. Used for quick, stateless calculation capabilities (e.g. database reads, mathematical projections).
- **Asynchronous Execution**: Return a tracking `taskId` immediately. The task operates in the background, emitting lifecycle events (`task.started`, `task.progress`, `task.completed`). Used for agent actions, simulations, and human-in-the-loop approvals.

### 2. Idempotency and Deduplication Semantics
To prevent double execution of critical operations:
- Every task must carry a `deduplicationKey`, generated by hashing:
  $$\text{deduplicationKey} = \text{SHA256}(\text{taskName} + \text{correlationId} + \text{JSON.stringify(inputs)})$$
- The E-COS Execution Engine checks the key against a cache. If the key exists:
  - If the task is *completed*, the engine returns the cached output instantly without re-executing.
  - If the task is *in_progress*, the caller is subscribed to the active task's resolution event instead of starting a new process.

### 3. Retry and Backoff Semantics
When transient errors occur, tasks must be retried utilizing Exponential Backoff with Decorrelated Jitter:
- **Base Formula for delay**:
  $$t_{\text{sleep}} = \min(t_{\text{max}}, t_{\text{base}} \times 2^{\text{attempt}}) + \text{random}(0, \text{jitter})$$
- Default limits: `maxAttempts: 3`, `baseDelay: 1000ms`, `maxDelay: 30000ms`.
- Non-retryable errors (e.g. `ERR_UNAUTHORIZED`, `ERR_INVALID_INPUT`) bypass retries and fail immediately.

### 4. Saga Transaction and Compensation Protocol
For multi-step operational plans (e.g., reserving a resource, allocating budget, launching ads), if a downstream step fails and cannot recover:
- Runtimes must execute the Saga compensation protocol in reverse order of execution.
- Every stateful step must register a `compensate` function containing rollback actions:
  ```typescript
  export interface SagaStep {
    id: string;
    action: () => Promise<any>;
    compensate: () => Promise<void>; // Reverts state change
  }
  ```

### 5. Timeouts, Cancellations, and Signals
- Every asynchronous task execution must accept a standardized cancellation signal wrapper:
  ```typescript
  export interface ExecutionSignal {
    aborted: boolean;
    reason?: string;
    onAbort(callback: () => void): void;
  }
  ```
- If a timeout (e.g., user-defined limit of 30 minutes) is hit or a user manually triggers a cancellation, the task runner calls `abort()`, forcing runtime threads and capabilities to immediately release locks and exit.

## Consequences
- **Financial & Resource Safety**: Idempotency checks guarantee that money and compute resources are never wasted on redundant execution runs.
- **Fail-Safe Recovery**: Sagas guarantee that the company state is rolled back cleanly to a stable condition instead of leaving corrupted, semi-executed operations.
- **Controlled Concurrency**: Timely timeouts and cancel signals free thread resources, avoiding zombie agents or memory leaks.
