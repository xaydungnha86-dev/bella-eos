# ADR-0014: Enterprise Canonical Data Model

* **Status**: Draft
* **Date**: 2026-07-29
* **Author**: Enterprise Architecture Board

## Context
As E-COS handles distributed processing across diverse runtimes (Executive C-Level, Operational Planning, Resource Allocation, and Execution), there is a significant risk of semantic drift. For instance, a `Goal` might be represented as a metric string in one runtime, but a structured target in another. 

To ensure complete interoperability, we require an **Enterprise Canonical Data Model (ECDM)**. This model defines the unified, immutable schemas for all core enterprise concepts, allowing runtimes to exchange and persist data without transformation layers.

## Decision
All E-COS runtimes and database capabilities must utilize the following unified schemas for core business entities:

```
    ┌─────────────────────────────────────────────────────────┐
    │              Enterprise Canonical Data Model            │
    ├──────────────┬──────────────┬─────────────┬─────────────┤
    │              │              │             │             │
    ▼              ▼              ▼             ▼             ▼
┌───────┐     ┌─────────┐     ┌───────┐     ┌──────────┐  ┌───────────────┐
│ Goal  │     │  State  │     │ Task  │     │ Decision │  │   Capability  │
└───────┘     └─────────┘     └───────┘     └──────────┘  └───────────────┘
```

### 1. Goal and GoalGraph Schema
Represents corporate intentions, constraints, and dependencies:

```typescript
export interface Goal {
  id: string;               // UUID
  parentId?: string;        // For sub-goal decomposition
  title: string;
  description: string;
  metric: {
    name: string;           // E.g., "Revenue", "CAC"
    unit: string;           // E.g., "M VND", "USD"
    baseline: number;
    target: number;
    current: number;
  };
  timeline: {
    start: string;          // ISO Date
    deadline: string;       // ISO Date
  };
  constraints: {
    type: 'budget' | 'workforce' | 'policy' | 'market';
    description: string;
    value: any;
    status: 'monitoring' | 'warning' | 'blocking';
  }[];
  urgency: 'low' | 'medium' | 'high' | 'critical';
  status: 'pending' | 'active' | 'achieved' | 'failed';
}

export interface GoalGraph {
  nodes: Goal[];
  edges: {
    from: string;           // Goal ID
    to: string;             // Goal ID
    type: 'requires' | 'influences' | 'conflicts';
  }[];
}
```

### 2. Enterprise State Schema
A unified state registry partitioned into logical areas, queried by the C-Level and Planning layers:

```typescript
export interface EnterpriseState {
  business: {
    currentRevenue: number;
    customerCount: number;
    conversionRate: number;
    churnRate: number;
    customMetrics: Record<string, number>;
  };
  runtime: {
    activeWorkflows: number;
    systemLoad: number;
    activeAgents: number;
    failedTaskRate: number;
  };
  resource: {
    tokenSpendToday: number;
    apiBudgetRemaining: number;
    activeLicenses: Record<string, number>;
  };
  human: {
    activeFTEs: number;
    allocatedFTEs: number;
    departmentalCapacity: Record<string, number>; // E.g., { marketing: 8, ops: 10 }
  };
  timestamp: string;
}
```

### 3. Task Schema
The basic unit of work generated by the Planning Runtime (PLR) and executed by the Execution Layer:

```typescript
export interface Task {
  id: string;               // UUID
  workflowId: string;       // Core workflow coordination ID
  title: string;
  description: string;
  status: 'backlog' | 'ready' | 'in_progress' | 'completed' | 'failed' | 'cancelled';
  assignedTo: {
    type: 'agent' | 'human' | 'system';
    id: string;             // Agent ID / Worker ID
  };
  dependencies: string[];   // Precedent Task IDs
  inputs: {
    name: string;
    schemaType: string;
    value: any;
  }[];
  outputs: {
    name: string;
    schemaType: string;
    value: any;
  }[];
  metrics?: {
    startedAt: string;
    completedAt: string;
    costIncurred: number;
    retryCount: number;
  };
}
```

### 4. Decision Schema
The immutable record representing executive approval for corporate actions, persisted in the immutable decision chain ledger (Tier 11):

```typescript
export interface Decision {
  decisionId: string;       // Decision #DXXXX
  timestamp: string;
  authorizer: string;       // Principal ID (e.g. CEO)
  sessionRef: {
    sessionId: string;
    traceId: string;
  };
  originalGoal: Goal;
  agreedGoal: Goal;
  alternatives: {
    target: number;
    probabilitySuccess: number;
    budget: number;
    primaryRisk: string;
  }[];
  debateTrace: {
    agent: string;
    action: 'debate' | 'propose' | 'modify' | 'approve';
    message: string;
    timestamp: string;
  }[];
  evidenceCollected: {
    category: string;
    metric: string;
    delta: string;
    description: string;
  }[];
  finalApproval: {
    status: 'approved' | 'rejected';
    approvedBy: string;
    comments: string;
    timestamp: string;
  };
}
```

## Consequences
- **Zero-Transformation Integration**: Inter-runtime messaging utilizes the exact same object schemas, removing the overhead of parsing and translating data structures.
- **Unified State API**: The Digital Twin and AI Executives can query `EnterpriseState` at a single endpoint instead of scraping multiple decentralized registries.
- **Integrity Validation**: Static DAG analysis can check tasks and goals for cycles or missing requirements instantly.
